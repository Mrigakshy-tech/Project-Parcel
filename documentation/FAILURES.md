# Project Parcel — Failures and Recovery Log

This log records issues observed while building and running the synthetic Project Parcel notebook. The dataset and all results in this exercise are synthetic; they are not company production data.

## 1. Pandas nullable-string / scikit-learn compatibility error

**What happened:** During model fitting and later evaluation, scikit-learn raised a `TypeError` in its missing-value handling (`_object_dtype_isnan`). The traceback ended with `TypeError: boolean value of NA is ambiguous`.

**What I initially believed:** The categorical columns had been normalized and the train/validation split was ready for modeling, so I expected the model pipeline to receive ordinary Python/NumPy missing values.

**What caused it:** Pandas nullable `string` columns can represent missing values using `pd.NA`. Some scikit-learn/pandas combinations encountered that sentinel while checking object arrays for missing values. The test split also needed the same compatibility treatment; fixing only train and validation was incomplete.

**What I tried:** I first converted nullable string columns in the training and validation dataframes to `object` and replaced missing values with `np.nan`. The evaluation step still failed when the test dataframe retained pandas nullable values.

**Resolution:** Apply the compatibility conversion consistently to **train, validation, and test** feature columns before evaluation. Nullable string columns are converted to ordinary object dtype and missing entries are represented as NumPy `np.nan`. Object columns are also normalized so pandas `pd.NA` does not remain. The notebook includes a compatibility cell and a follow-up check across all three splits.

**What I learned:** Data type compatibility must be checked across every split and every model-inference path, not just the training dataframe. A successful fit does not guarantee that validation or test inference will accept the same data representation.

## 2. Cost-minimizing threshold exceeded review capacity

**What happened:** Under the illustrative false-negative cost of 5 and false-positive cost of 1, the validation cost-minimizing threshold was 0.29. It flagged 1,037 of 1,200 validation shipments (86.4%), including 699 false positives.

**What I initially believed:** A threshold selected from the cost ratio might provide a practical intervention rule.

**What I learned:** Minimizing the assumed classification cost alone does not enforce the separate operational constraint that the team can review only 10% of shipments. The threshold rule is therefore infeasible under the assumed capacity.

**Decision:** Use a top-10% risk-ranking queue (120 of 1,200 shipments) for the demonstration. This is a capacity-constrained prioritization rule, not a claim that it minimizes total cost. The 5:1 cost ratio and 10% review capacity are illustrative assumptions and must be validated with operations.

## 3. Limited recall under the top-10% review policy

**What happened:** On the held-out synthetic test period, the top 120 shipments achieved 65.83% precision but only 18.33% recall.

**What I learned:** The queue is enriched for late parcels, but it misses most late parcels. It is useful only as a prioritization aid and must not be represented as a complete late-shipment detector.

**Next step:** Test alternative capacity levels and intervention strategies on real, time-stamped data; measure the cost and benefit of interventions; and consider whether additional early-warning signals can improve recall without exceeding operational capacity.

## 4. Drift-monitor check

**What happened:** The ordinary held-out test batch produced no drift alerts. A deliberately shifted `distance_km` test batch triggered a high-PSI alert (PSI approximately 12.43).

**What I learned:** The deliberate shift verifies that this particular monitoring check can detect a large distribution change. No alert on one synthetic test batch does not establish that future production data will be stable or that the monitor catches every meaningful form of drift.

## 5. Data and deployment limitations

- All data are generated by a synthetic generator; performance metrics do not establish real-world logistics performance or savings.
- False-negative cost 5, false-positive cost 1, and 10% review capacity are illustrative assumptions, not measured company values.
- Features such as `carrier_historical_ontime_rate` and `planned_load_ratio` require timestamped, dispatch-time definitions to rule out leakage in a real deployment.
- Segment metrics can be noisy for small groups; low-volume segments should not be over-interpreted.
- The model misses many late shipments under the selected top-10% policy. Broader operational monitoring remains necessary.
